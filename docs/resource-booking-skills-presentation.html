01 / Context

A booking tool with real rules

Reserve shared rooms and equipment without overlapping bookings.

  • Seven resources, with day/week calendars and a booking list.
  • Email demo identity, ownership-aware cancellation and browser persistence.
  • Clear conflict feedback and usable desktop/mobile workflows.

Scope: a browser-only MVP. Real authentication, a backend and deployment remain outside this delivery.

04 / Design research output

A visual reference became a UI contract

What the skill made concrete

  • Composition: header, resource deck, filters and schedule.
  • Tokens: blue primary, neutral surfaces, system typography and spacing guidance.
  • Responsive behavior: seven cards on wide screens, a scrolling deck and Filters sheet on mobile.
  • Implementation mapping: Tailwind, Radix-based shadcn primitives and FullCalendar Standard.

The prototype uses custom HTML/CSS/JavaScript. Its in-memory demo model is separate from the app’s persistence and rules.

06 / Engineering examples

Concrete checks protect booking behavior

01

Intervals

Half-open intervals allow 10:00–11:00 followed by 11:00–11:30. A booking at 10:30 conflicts on the same resource.

domain/bookings.ts
02

Identity & ownership

Use cases resolve the current demo user. Domain cancellation rejects a different owner even when called directly.

application/use-cases.ts
03

Storage failures

Stored values pass schema validation. Multi-key writes attempt rollback and report failure rather than silently succeeding.

storage/safe-storage.ts

These are observable implementations of the skill’s contract and failure-handling principles. Demo identity and localStorage do not provide production security or cross-tab atomicity.
